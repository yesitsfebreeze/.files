## `Ctrl+Shift+D`

**Drop this directory into a capsule**

*Terminal*

Press `Ctrl+Shift+D` in any pane: `capsule` runs on that pane's directory and you end up at a shell in `/workspace` inside the container, with the directory's contents there and your credentials working. Press it again later and you are back in the same running container, immediately.

<Callout title="Why it is this way">
The binding is a thin wrapper over the CLI, not a second implementation — same container name, same image, same mounts, which is checkable by diffing `docker inspect`. The old config had two entry paths that drifted apart, and that is the mistake being avoided. It is one of the four keys the terminal still owns after the multiplexer took the rest: it types into the pane rather than addressing it.
</Callout>

## `Ctrl+Shift+B`

**Rebuild the capsule image and start over**

*Terminal*

Press `Ctrl+Shift+B` to run `capsule --rebuild` for this directory: the image is built again and the container recreated. Reach for it when you changed the image on purpose, or when a container has gone strange.

<Callout title="Why it is this way">
The key looked contested — in the live config control+shift+B prompts for a desktop wallpaper — but that whole pipeline is rated DO NOT PORT, so it comes free with the port and there is nothing left to settle. Why a rebuild is ever needed at all lives on `capsule --rebuild`, not here.
</Callout>

## `Ctrl+Shift+S`

**Reopen a recent workspace here**

*Terminal*

Press `Ctrl+Shift+S` and a fuzzy-selectable list of the directories you have most recently mounted opens, newest first: type to narrow it, then choose, and that directory's capsule is mounted in this pane. Directories that no longer exist are dropped as the list is read.

<Callout title="Why it is this way">
The list is written by the capsule tool on every successful mount, not by the terminal, so it is the same list however you started the container — and it survives restarting the terminal. The `Recent:` indicator this entry used to promise is gone with the derived status bar: the bar is the multiplexer's now and nothing sets its left side from a picker.
</Callout>

## `Ctrl+Shift+O`

*Terminal*

Same picker as `Ctrl+Shift+S`, but it opens in a new OS window and leaves the pane you were in alone.

<Callout title="Why it is this way">
A window, not a tab, and that is the point: there are no tabs. This key replaced `Ctrl+Shift+T`, which was documented as an open collision — it was the terminal's own new-tab default AND the tab reconciler's manual path, so the drift check passed off the default alone whether or not a capsule binding was ever written. ## `capsule [dir]`

**Drop a directory into a dev container**

*Shell*

Run `capsule` to put the current directory in a container, or `capsule <dir>` for another one. You land in zsh at `/workspace`, which is the directory itself — edits inside are edits outside. Run it again in the same directory and, if the container is still running, you are back in it in well under a second; if it was stopped it starts and attaches, and if the image definition changed it rebuilds the image first, which takes as long as docker takes. Every successful mount is recorded for the recent-workspace picker.

<Callout title="Why it is this way">
One container per directory, named after it, with a short path hash appended so two directories called `api` in different parents do not collide. This one command replaced five loosely coupled pieces — a terminal binding, a shell function, a task-runner recipe, a second Dockerfile and a credential script — that overlapped and drifted.
</Callout>

## `capsule --rebuild`

**Rebuild the image and recreate the container**

*Shell*

`capsule --rebuild` builds the image again and throws away the existing container for this directory before making a new one. Anything you left in the container's own filesystem, outside `/workspace`, is gone.

<Callout title="Why it is this way">
The only way to force a rebuild. A changed image definition is picked up automatically on the next mount; nothing else rebuilds implicitly, because an implicit rebuild in the middle of a working day is the thing that makes people stop using the tool.
</Callout>

## `credentials in a capsule`

**Understand how a container gets your credentials**

*Container*

Nothing to run: inside a capsule, `git pull`, `git push` over either protocol, `ssh -T git@github.com`, `claude` and `opencode` all just work, with no login and no prompt.

<Callout title="Why it is this way">
Everything arrives by mount, never in an image layer — `docker history` shows no credential material. `.gitconfig` is mounted read-only so authorship matches the host. The HTTPS credential is exported from the host's credential helper into a cache directory the container reads as its git credential store — synchronously on create and on `--rebuild`, backgrounded on any attach to an existing capsule, and on either path skipped while every exported file is under 60 seconds old, because the four-file export costs ~1.5s (git's helper 0.75–1.16s, an agent keychain read 0.34–0.50s) — over the whole warm-attach budget. That path is bound as a directory, never file by file: the refresh renames each file into place, so a rotated token reaches an already-running capsule.
</Callout>

## `ssh in a capsule`

**Understand how SSH works inside a capsule**

*Container*

Nothing to run: inside a capsule, `ssh -T git@github.com`, `git pull` and `git push` over SSH all just work, with no host-key prompt.

<Callout title="Why it is this way">
Keys are copied into a container-local directory rather than used from the read-only mount, because Docker Desktop's file sharing does not carry host permissions into the container in a form ssh accepts. The copy gets the mode each file needs: 700 on the directory, 600 on private keys and the generated config, 644 on `*.pub` (`setup-credentials.sh:59,67,68`). The no-prompt guarantee is `StrictHostKeyChecking accept-new` (`:115`), which accepts an unseen host key once rather than disabling verification the way `no` would. The `ssh-keyscan -T 5` pre-add (`:121-130`) is the optimisation, not the guarantee: it seeds `known_hosts` before the first connection when the network allows it, and `accept-new` covers the connection when it does not.
</Callout>
