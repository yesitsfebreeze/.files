# spec02 — the container side: one first-run setup script

Write `home/dot_config/capsule/executable_setup-credentials.sh`, which
chezmoi deploys to `~/.config/capsule/setup-credentials.sh` (mode `0755`, the
`executable_` prefix; `home/dot_config/television/executable_theme-preview.sh`
is the precedent). spec01 mounts it read-only at
`/opt/capsule/setup-credentials.sh` and runs it once, as `dev`, on the create
path. It turns the read-only mounts into working SSH, git and agent auth
inside the container — and nothing it writes ever leaves the container.

It lives beside the Dockerfile because that is the tool's config directory,
but note what that means: `~/.config/capsule` is also the docker **build
context**. A script there is fine (the Dockerfile has no `COPY`/`ADD`, and
C.1's gate keeps it that way); a credential there would be one `COPY .` from
a layer. Never write generated material into this directory.

## What it may assume

- It runs as `dev` (uid 1001), the image's unprivileged user (C.1 R5). It
  needs **no** root and must call neither `sudo` nor `useradd`: the image
  already creates the user, which is the single biggest simplification over
  the legacy `setup-user.sh` — that script created users, edited
  `/etc/sudoers`, and cloned a dotfiles repo over SSH before any credential
  was known to work.
- The image has `git`, `openssh-client`, `bash`, `zsh` and coreutils
  (C.1 R2 plus its support set). It may install nothing — the toolbox is
  closed (C.1 R7).
- Mount layout, all read-only and all optional except the creds directory:
  `/opt/capsule/host/ssh`, `/opt/capsule/host/gitconfig`,
  `/opt/capsule/creds` (`git-credentials`, `claude-credentials.json`,
  `claude.json`, `opencode-auth.json`).

`set -eu` plus a trailing "done" line, and every optional source guarded:
a missing source is one warning on stderr and a continue, never an abort.
The script must be **idempotent** — `capsule --rebuild` re-runs it, and so
may a human debugging inside a capsule.

## What it does

### 1 — SSH (R1)

`install -d -m 700 ~/.ssh`, then from `/opt/capsule/host/ssh`:

- copy every `id_*` that is not `*.pub` to `~/.ssh/`, `chmod 600`;
- copy every `id_*.pub` to `~/.ssh/`, `chmod 644`;
- copy `known_hosts` if present, `chmod 600`;
- copy **nothing else** — explicitly not the host's `~/.ssh/config` and not
  `.DS_Store`. The host config is macOS-shaped: on this machine it is
  `Include ~/.orbstack/ssh/config`, a path that does not exist in the
  container, and the common macOS `UseKeychain yes` line makes Linux `ssh`
  abort *every* invocation with "Bad configuration option: usekeychain". The
  legacy script did `cp -a` of the whole directory and inherited exactly
  that risk.

Copying rather than using the mount directly is R1's point and it has a
reason: Docker Desktop's macOS file sharing does not carry host file modes
into the container in a form ssh will accept, and ssh refuses a private key
it considers group- or world-readable ("Permissions … are too open"). The
mount stays read-only; the usable copy is container-local, so fixing modes
can never change the host's keys.

Then write `~/.ssh/config` (mode `600`) ourselves — generated, not inherited:

```
# generated by capsule's first-run credential setup
Host github.com
  IdentityFile ~/.ssh/<each private key copied, LC_ALL=C sorted>
  IdentitiesOnly yes
  UserKnownHostsFile ~/.ssh/known_hosts
  StrictHostKeyChecking accept-new
```

One `IdentityFile` line per copied private key rather than a guessed
"preferred" name — this host has both `id_gh` and `id_rsa`, and ssh tries
each. `IdentitiesOnly yes` keeps ssh from offering anything else. Keep the
key count small: more than about five keys and GitHub answers "Too many
authentication failures" before reaching the right one.

Host keys: if `~/.ssh/known_hosts` has no `github.com` line, append
`ssh-keyscan -t rsa,ecdsa,ed25519 github.com` output, best-effort (it needs
network; a failure is a warning, not an abort). `StrictHostKeyChecking
accept-new` is the backstop that keeps the first connection from prompting
when keyscan could not run. Never `StrictHostKeyChecking no` — that disables
host verification entirely instead of just the prompt.

### 2 — git identity and HTTPS credentials (R2, R3)

Write `~/.gitconfig` (mode `600`, container-local and writable, so
`git config --global` inside a capsule still works):

```
# generated by capsule's first-run credential setup — container-local
[include]
	path = /opt/capsule/host/gitconfig
[credential]
	helper =
	helper = store --file=/opt/capsule/creds/git-credentials
[credential "https://github.com"]
	helper =
	helper = store --file=/opt/capsule/creds/git-credentials
[credential "https://gist.github.com"]
	helper =
	helper = store --file=/opt/capsule/creds/git-credentials
[core]
	pager = less -FRX
[interactive]
	diffFilter = cat
```

Every line after the include is a correction to something the host config
does that cannot work in a container, and each one costs a debugging session
if it is dropped:

- The host routes github.com through `helper = !gh auth git-credential`
  (verified in `~/.gitconfig` and in `home/dot_gitconfig.tmpl`). `gh` is
  **not** in the image's closed toolbox, so an inherited helper makes every
  HTTPS push shell out to a missing binary. The `helper =` reset then the
  store helper is the same trick the host config itself uses — and it must
  be repeated **per URL**, because a URL-scoped helper list overrides the
  generic one; a top-level reset alone leaves `!gh auth git-credential` in
  place for github.com, which is the whole point of the exercise.
- `core.pager = delta` and `interactive.diffFilter = delta --color-only` are
  inherited from the host, and `delta` is not in the image either — without
  the override, `git diff` and `git log` fail inside every capsule. `cat` is
  a no-op filter; leaving `diffFilter` empty makes git run an empty command.
- The include is what satisfies R2: author, committer, aliases and every
  other host preference arrive from the mounted file, so authorship inside a
  capsule matches the host without copying anything.
- The host's `[includeIf "gitdir:~/dev/_pi_extensions/"]` names a path that
  does not exist in the container. Git ignores a missing include silently, so
  nothing is owed — noted so nobody "fixes" it.

The credential store file is read straight from the read-only mount. Nothing
is copied, which is what makes a rotated token heal: spec01 rewrites that
file on the host and a running container sees the new content immediately.
`git credential-store` only writes on `approve`, which git does not call for
a credential a helper supplied, so a read-only store is the normal path and
not a lurking error.

### 3 — the agents (R4)

Claude Code:

- `install -d -m 700 ~/.claude`
- `ln -sfn /opt/capsule/creds/claude-credentials.json
  ~/.claude/.credentials.json`
- `install -m 600 /opt/capsule/creds/claude.json ~/.claude.json`

A **symlink** for the credential and a **copy** for `.claude.json`, and the
asymmetry is the interesting part:

- The credential is symlinked into the read-only mount so a host-side
  refresh reaches even a running capsule, and so the container physically
  cannot write a token anywhere. It also cannot perform its own OAuth
  refresh — which is deliberate: Claude's refresh **rotates** the refresh
  token, so a capsule that refreshed on its own would invalidate the host's
  login. Borrowing the host's credential and failing closed is the correct
  trade. The visible failure mode, which belongs in the manual checklist: if
  the access token expires while a long-lived capsule sits idle, `claude`
  inside it asks to log in, and re-mounting (or running `claude` on the
  host) heals it.
- `.claude.json` is written by Claude Code on every run, so it must be
  writable and container-local; a symlink into the read-only mount would
  make the agent fail on startup. It is the filtered six-key projection
  spec01 writes, so the copy carries onboarding state and account identity
  and no token.

OpenCode:

- `install -d -m 700 ~/.local/share/opencode`
- `ln -sfn /opt/capsule/creds/opencode-auth.json
  ~/.local/share/opencode/auth.json`

Same reasoning. Everything else OpenCode writes — its database, logs,
snapshots — stays container-local, which is the point: the host's 94 MB
SQLite store is not shared into a container.

Each of the four is skipped with a warning when its creds file is absent, so
a host with no Claude login still gets a working capsule.

### 4 — what it must never do

- Never `chmod`, `chown` or write anything under `/opt/capsule/**`. Those
  are the read-only host mounts.
- Never write outside `$HOME`.
- Never print a credential, not even truncated: it runs with its output on
  the user's terminal, and a token in the scrollback is a token in the
  scrollback.
- Never install a package, and never create a user.
